A. REAL BUGS (found by the audit, confirmed in code)
════════════════════════════════════════════════
1. An ADMIN without the "invites" power cannot open Snow Team at all.
   The database helper the snow team functions use was changed (update 66) to require
   the invites permission, so list/change/remove snow access and the Team Access list
   all answer "Only the owner can do this" for such an admin. Owner unaffected.
2. "Add Worker" does nothing inside Snow Mode.
   The button opens an owner-mode screen; the app's router immediately bounces you
   back to the snow dashboard. Works from landscaping mode only.
3. Tapping a push notification while in Snow Mode does nothing.
   The notification router only knows landscaping screens, so owner stop alerts
   can't be opened from the snow shell.
4. "Save as template" saves templates that NOTHING can use.
   The "start a route from a template" side was removed at some point; saving remains.
   Half a feature. Either remove the button or restore "from template".
5. Deleting a company misses Snow-only workers.
   Their logins survive (they land on "Finish setting up") and their files are not
   queued for cleanup. (SQL fix, for the ledger.)
6. A silent trap around sign-in for Snow-only workers.
   Sign-in still calls an old function that reads the dead snow-requests table and
   swallows any error. If we ever drop that table first, Snow-only workers would be
   silently treated as having no company. Fix: switch sign-in to the newer function
   first, then the old one can go.
7. A draft storm can end up with NO route, with no message.
   The storm screen auto-creates the route and ignores most failures; after that it
   never retries. Also: cancelling a storm's only route quietly creates a new blank
   one next time the storm opens.
8. The Snow Properties list goes stale.
   After adding a property and turning services on, going back still shows
   "No services on yet" until a manual refresh.
9. "Customer messages" switches: a mixed state shows as Off, and a property added
   later gets the default (finished=on, arrives=off) instead of your choice. Honest
   fix is one company-level setting; today it writes per property.

F. VS JOBBER (what's missing, what's better)
════════════════════════════════════════════════
Worth building (ranked by value for one company):
1. Push the crew lead a notification when a storm is DISPATCHED (and when their
   route changes). Today they only find out by opening the app — at 3am that's the
   weak link. Small job; the notification plumbing already exists.
2. Money: completed snow visits never reach invoices. No price on a property's
   snow services, and you retype storm work into landscaping invoices by hand.
   A per-property price + "End Storm -> draft invoice" closes the loop. Bigger job,
   but it's the biggest gap; everything it needs already exists.
3. "Optimize stop order" button: properties already store map coordinates, nothing
   uses them for ordering. A simple nearest-first sort into the existing reorder
   would do it. Medium job.
Not worth it for your size (my take): season-contract billing engines, customer
ETAs ("you're 3rd in line"), live GPS crew maps, weather-triggered auto-storms.
What this app does BETTER than Jobber for snow (don't break these): storms as a
real object with a draft->dispatched->ended lifecycle; photo proof with an owner
review gate before customers see anything; the skip-request approval flow;
versioned per-property instructions; everything enforced server-side and safe to
double-tap on a bad connection.
